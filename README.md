# School Uniform Sales

Point-of-sale for a school uniform shop: record a sale, print a receipt, export
the month to Excel. English and French.

Next.js 16 (App Router) · Supabase · next-intl · shadcn/ui · Tailwind v4 · SheetJS

## Getting started

```bash
npm install
cp .env.example .env.local   # then fill in the Supabase values
npm run dev
```

Until `.env.local` holds real Supabase credentials every route redirects to
`/en/login`, which renders but cannot sign anyone in. That is deliberate — an
unconfigured app behaves like a signed-out one instead of crashing.

Database setup lives in [`supabase/README.md`](supabase/README.md).

## How the pieces fit

**Locale then auth.** `src/middleware.ts` runs the next-intl middleware first
and lets it own the response, then decorates that same response with refreshed
Supabase cookies. Two middlewares each constructing their own `NextResponse`
would drop one another's `Set-Cookie` headers. The auth guard runs last, on the
locale-stripped path.

**Totals are computed twice, trusted once.** `computeTotals()` in
`lib/validation/sale-schema.ts` drives the running total in the form, and
`createSale` calls the same function again on the server. Only the server's
numbers are written. Likewise `seller_id` comes from the session, never the
payload.

**Receipts are self-contained.** `sale_items` stores description, size and unit
price rather than pointing at the live catalogue, so reprinting a six-month-old
receipt shows the price that was actually charged.

**RLS is the access control, not the UI.** A seller sees their own sales; an
admin sees all. The Excel export runs the same query under the same policies,
so who can export what needs no separate check. Policies live in
`supabase/policies/` as re-appliable SQL.

**The ledger is append-only.** No table grants a delete policy. Stock is
corrected with a compensating movement, not an edit.

## Scripts

| | |
|---|---|
| `npm run dev` / `build` / `start` | Next.js |
| `npm run lint` / `typecheck` | ESLint / `tsc --noEmit` |
| `npm run db:start` / `db:stop` | local Supabase (needs Docker) |
| `npm run db:push` | apply migrations |
| `npm run db:policies` | apply `supabase/policies/*.sql` (needs `psql` + `SUPABASE_DB_URL`) |
| `npm run db:reset` | replay migrations + seed locally |
| `npm run db:types` | regenerate `src/types/database.types.ts` |

## Phase 2

Schema, RLS and Server Actions for stock are already in place
(`supabase/migrations/20260101000100_stock.sql`, `src/actions/stock.ts`); the
screens are not. Two flags gate the rest:

- `ENABLE_SIGNATURE` in `components/forms/sale-form.tsx` — the signature pad and
  the `sales.signature_url` column both exist, capture is switched off.
- `deductStockForSale()` in `actions/stock.ts` is written but not called from
  `createSale`, so sales don't yet move stock. Wire it in once counts are being
  kept accurate, otherwise you get negative balances that look like real data.

## Notes

- `src/middleware.ts` logs a deprecation warning on Next 16, which now prefers
  `src/proxy.ts`. The old name still works and is what next-intl documents;
  migrate with `npx @next/codemod@canary middleware-to-proxy .` when convenient.
- SheetJS is installed from `cdn.sheetjs.com`, not npm. The `xlsx` package on
  the public registry is a stale 0.18.5 with known advisories; the vendor
  publishes current releases only from their own CDN.
